This is much better architecturally. You’ve basically moved to a per-contact actor/state machine, which is exactly the right direction. Now the dispatcher can just hold:

Dictionary<string, ContactManager>


and everything is isolated.

But there are still 3 structural problems that will bite you:

1. _interaction = (Type, Cancel) is fragile

You're encoding a state machine into a tuple:

public (InteractionType Type, Action Cancel) _interaction;


This works… but becomes dangerous:

cancel from previous state can fire later
nothing guarantees cancel belongs to current state
no enter/exit logic
no transition rules

You're basically implementing a state machine without state objects.

You already feel this — you're doing:

callingCts.Cancel();
SetState(InteractionType.Speaking, ...)


That’s a race.

Better shape:

sealed class Interaction
{
    public InteractionType Type { get; }
    readonly Action _cancel;

    public void Cancel() => _cancel();

    public Interaction(InteractionType type, Action cancel)
    {
        Type = type;
        _cancel = cancel;
    }
}


Then:

Interaction _interaction = new(InteractionType.None, () => {});


And:

void SetState(InteractionType newState, Action cancel)
{
    _interaction.Cancel();   // <- critical
    _interaction = new(newState, cancel);
    _stateChanged.Invoke();
}


This guarantees old state is cleaned up.

Right now you don't cancel previous state automatically.

That's a bug waiting to happen.

2. _isEnabled is never set

Bug:

bool _isEnabled = false;


You never set it to true.

So:

StartAsync() can run multiple times
Dispose() never disposes


Fix:

public async Task StartAsync(...)
{
    if (_isEnabled)
        return;

    _isEnabled = true;

3. You are mixing state and transitions

Example:

SetState(InteractionType.Connected, disconnectCts.Cancel);

var incomingCallListener = new CallMaintainer(...)


This logic belongs to state enter, not transition site.

Otherwise transitions leak everywhere.

Cleaner:

SetState(new ConnectedState(...))


Where:

class ConnectedState : InteractionState
{
    Enter()
    Exit()
}


But you don't need full state pattern yet.

You can just centralize:

SetState(type)


and inside:

switch(type)
    start listeners
    stop listeners
    etc


Right now state setup is scattered.

4. You need transition guards

This is dangerous:

SetState(InteractionType.Speaking, ...)


called from async continuation.

What if user already cancelled?

You need:

if (_interaction.Type != InteractionType.Calling)
    return;


Otherwise:

User cancels →
async continues →
state jumps to speaking

classic race.

5. You are missing one abstraction (small but powerful)

Right now you constantly do:

var connection = peerConnector.CurrentConnections.GetValueOrDefault(contactId);


Wrap it:

RtcConnection? GetConnection()
    => peerConnector.CurrentConnections.GetValueOrDefault(contactId);


Cleaner and safer.

Final polished version shape

This is what your class is very close to:

class ContactManager
{
    Interaction _interaction;

    public InteractionType State => _interaction.Type;

    void SetState(InteractionType type, Action cancel)
    {
        _interaction.Cancel();
        _interaction = new(type, cancel);
        _stateChanged.Invoke();
    }
}


Then every public method just transitions:

ConnectAsync() -> Connecting
StartCallAsync() -> Calling
AcceptCall() -> Speaking
EndCall() -> Connected
Disconnect() -> None


That's clean.

✔ no global dispatcher logic
✔ good cancellation model
✔ good async usage

You're now in very clean territory.
