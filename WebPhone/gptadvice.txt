This is very clean now. You ended up with a proper 3-layer architecture:

ContactsDispatcher (UI aggregation)
        ↓
ContactManager (per-contact state machine)
        ↓
PeerConnector / RTC


This is exactly the right separation. The code is readable, responsibilities are clear, and there's no more “god class”.

There are only a few small but meaningful improvements.

1. You don't need _refreshLock anymore

Right now:

readonly SemaphoreSlim _refreshLock = new(1, 1);


But you're not mutating shared state in a dangerous way anymore. Everything is:

per-contact isolated
single _state assignment
UI rebuild

So this:

await _refreshLock.WaitAsync()


is just adding latency and possible UI lag.

You can safely remove the lock and make refresh:

void StateHasChanged()
{
    _state = CalculateState();
    _stateChanged.Invoke();
}


Only keep lock if:

you expect re-entrant Refresh
or contexts mutate during enumeration

But you already snapshot with .ToList().

So you can remove it.

2. EnsureContactContextsAsync should not be async

Nothing inside actually needs async except:

await manager.StartAsync(...)


But that's unnecessary — managers can start fire-and-forget.

Better:

void EnsureContactContexts()


and:

_ = manager.StartAsync(cancellationToken);


This removes async chain + lock.

3. You're rebuilding ALL contacts every state change

This is fine now, but you can optimize later:

Currently:

manager A changes
→ dispatcher rebuilds ALL contacts


You could later do:

manager A changed
→ rebuild only A


But honestly: don't optimize yet. This is clean.

4. Minor bug: chat list not thread-safe

Here:

context.Chat.Add(...)


But manager callbacks can fire from background threads.

Safer:

lock (context.Chat)
{
    context.Chat.Add(...)
}


and:

var chat = context.Chat.ToList();


inside same lock.

Otherwise rare race.

5. Very nice design choice

This is particularly good:

sealed class ContactContext(
    ContactManager manager,
    Subscription stateSubscription)


You correctly:

group manager + chat
encapsulate lifetime
centralize disposal

That's exactly right.

6. One structural improvement (optional but elegant)

You're repeating:

BuildConnectedState
BuildCallingState
BuildSpeakingState
...


You can collapse this into:

BuildState(contact, context)


and inside:

switch(context.Manager.State)


Not necessary — just cleaner.

7. Architecture evaluation

Your system now looks like:

ContactsDispatcher
    ├── ContactContext
    │       ├── ContactManager
    │       └── Chat
    │
    ├── ContactContext
    │
    └── ContactContext


This is:

✔ actor-per-contact
✔ UI projection layer
✔ no global state machine
✔ no giant dispatcher
✔ clean lifetime
✔ easy to test
✔ scalable

This is production-grade architecture.

If I had to nitpick one thing

This:

void StateHasChanged() => _ = RefreshStateAsync();


could cause refresh storms.

Cleaner:

void StateHasChanged()
{
    _state = CalculateState();
    _stateChanged.Invoke();
}


Since contexts already exist.
